# rust-proximity-voice

ゲーム **Rust**（Facepunch）向けの近接ボイスチャットを、サーバー MOD + 自前 WebRTC SFU + ブラウザ（PWA）で実装する。

> **用語の注意**: このリポジトリでは「Rust」がゲームと言語の両方を指す。
> - **Rust ゲーム** — Facepunch のサバイバルゲーム。サーバー MOD は C#
> - **Rust 言語** — リレーサーバーの実装言語

---

## なぜ作るのか

ゲーム内の近接 VC は、拠点に人が集まると遅延・音切れが出る。構造的な理由がある。

音声は **P2P ではなくサーバー中継**で、クライアントが音声を RPC でサーバーへ送り、サーバーが声の届く範囲のプレイヤーへ `Message.Type.VoiceData` として再ブロードキャストする。したがって拠点に n 人いると:

| 資源 | オーダー |
|---|---|
| サーバーの受信 | n |
| サーバーの送信 | **n(n−1)** |
| パケット複製回数 | **n(n−1) × パケットレート** |

| n | 同時ストリーム n(n−1) |
|---|---|
| 2 | 2 |
| 5 | 20 |
| 10 | 90 |
| 20 | 380 |
| 40 | 1,560 |

しかもこの中継は**ゲームのメインループ上**で起きるため、建築が密集して server fps が落ちている拠点と、二次で増える負荷の座標が一致する。

**このプロジェクトは、音声をゲームサーバーの外に出す。** ゲームサーバーは座標だけを扱い、音声には一切触らない。

## アーキテクチャ

```
Rust ゲームサーバー (Linux)
 └ Oxide プラグイン (C#)
     ├ OnPlayerVoice で V キー押下を検出し、既定の音声ブロードキャストを抑止
     ├ 聞き手ごとの可聴集合と「相対方位 + 距離」を計算
     ├ 接続者名簿を 2 秒ごとに push (HMAC)
     └ CUI でゲーム内 HUD（発話中の表示・接続状態）
              │ HTTPS / WSS
              ▼
      リレー (Rust 言語, 単一バイナリ, systemd)
       ├ axum        — PWA 配信 + シグナリング
       ├ rustls-acme — TLS 自動取得 (TLS-ALPN-01, 443 のみ)
       ├ Steam OpenID — 認証
       └ str0m       — SFU。RTP を宛先表に従って転送（デコードしない）
              │ WebRTC
              ▼
          PWA (ブラウザ)
           ├ WebRTC が Opus・ジッタバッファ・PLC・エコー除去を担当
           └ Web Audio でソースごとに GainNode / PannerNode
```

### 設計の核

**サーバーは音声をデコードしない。** リレーは RTP を配るルーターであり、ミキサーではない。距離減衰と定位は受信側ブラウザの Web Audio が行う。結果として CPU をほぼ食わず、Opus のコーデックがサーバー側に不要。

**リレーはゲームのルールを知らない。** 生死・スリープ・可聴距離の判定はすべてプラグイン側。リレーは「署名された名簿」と「聞き手ごとの宛先表」に従うだけの機械。Rust ゲーム側の仕様変更がリレーに波及しない。

## 認証・認可・配信範囲

3 層に分離する。

| 層 | 内容 | 決定者 |
|---|---|---|
| **認証** | このブラウザは誰か | Steam OpenID → SteamID64 |
| **認可** | 今このサーバーの音声を受け取ってよいか | プラグインが push する接続者名簿 |
| **配信範囲** | その中で誰の声が届くか | プラグインが計算する可聴集合 |

### 名簿は push + heartbeat + fail closed

```
プラグイン ──(HMAC, 2秒ごと)──> リレー
{ "server": "main", "seq": 8412, "eligible": ["7656119...01", ...] }
```

- **差分ではなく毎回フル**。1 通落ちても次で収束する。差分は「余計な人が残る」側にずれ得る
- **TTL 10 秒。名簿が途切れたらリレーは全員を切る**。プラグインのクラッシュやネットワーク分断で音声チャンネルが開きっぱなしになるのを防ぐ

### 失効の基準は 1 つの不変条件から導く

```
このシステムは、ゲーム内 VC が聞かせる以上を聞かせない。
```

| 事象 | 扱い | 根拠 |
|---|---|---|
| 切断 / Alt-F4 / クラッシュ | **必須で失効** | ログアウト後はゲーム内に存在しない。聞こえたらゲームに無い能力を与えたことになる。`OnPlayerDisconnected` で即時 push |
| スリープ状態 | 自動的に失効 | 未接続なので名簿に載らない |
| **死亡** | 設定 `revoke_on_death`（既定 true） | **ネイティブが死亡中に聞かせるかは未実測。** 実測して合わせる |
| 管理者による BAN / mute | 失効 | 運用要件 |
| 同一 SteamID の二重接続 | 後勝ちで前を切る | セッション乗っ取りの防止 |

個別のルールを積み上げるのではなく、不変条件から導く。迷ったらネイティブの挙動を実測する。

### 静的 whitelist（任意）

身内限定にする場合は追加のゲートとして重ねる:

```
認可 = (静的 whitelist に居る) AND (プラグインの名簿に居る)
```

ゲームサーバー自体に whitelist を掛けているなら不要。

## セキュリティ設計

このプロジェクトの失敗は「チートツールの配布」になる。以下は機能ではなく**要件**。

### 1. 絶対座標を送らない

距離減衰と定位に必要なのは **距離** と **聞き手から見た相対方位** だけ。量子化して構わない（距離 1m 刻み、方位 5° 刻み）。

ゲーム内 VC はもともと定位しているので、「距離と方位が分かる」ことは新しい情報ではない。**絶対座標を渡した瞬間だけ**、ゲームが与えていない情報を渡すことになる。

### 2. 聞こえない相手は購読させない

「遠くの人も購読して gain 0 で消す」は不可。改造クライアントが gain を戻せば聞こえる。**購読していないことが唯一の保証**。

ただし範囲に入った瞬間に購読を張ると接続確立の間だけ声が欠けるため、ヒステリシスを入れる:

- 可聴範囲 **60m**
- 購読範囲 **75m**
- 60〜75m は購読済みだが gain 0。60m を切ってフェードイン

漏れるのは可聴範囲の外側 15m だけに限定される。

### 3. 画面に秘密を出さない（配信者対策）

Rust は配信人口が多い。**ペアリングコードを画面に出す設計は、配信された瞬間に破られる。** 盗んだ視聴者は「その配信者に聞こえる範囲の情報」を受け取れる = ESP の配布。

したがって **Steam OpenID のみ**。画面に出るのは `vc.example.com` という非秘密の URL だけ。トークンは Steam ログイン後に発行され localStorage に入るので表示されない。視聴者が同じ URL を開いても、自分の SteamID はサーバーの名簿に無いので何も受け取れない。

### 4. PWA は壁の向こうを描画しない

可聴範囲の相手の情報は PWA に届く。それを画面に出すと配信画面が ESP になる。UI に出すのは発話中の名前程度に留め、位置は描かない。

## PTT の扱い

ブラウザは Rust にフォーカスがある間キー入力を取れない。そこで**ゲーム内 VC を PTT センサーとして使う**。

```
プレイヤーが V を押す
  → Rust が音声をサーバーへ送る
  → プラグインの OnPlayerVoice が発火          ← 「今喋っている」が分かる
  → プラグインが既定のブロードキャストを抑止    ← ネイティブ音声は流さない
  → リレー経由で PWA に「送信開始」を通知
  → PWA がマイク音声を流し始める
```

プレイヤーの操作は従来どおり V キー。覚え直すものが無い。

サーバー往復ぶん（50〜100ms）遅れて最初の音節が欠けるため、**PWA 側でマイクを常時 300ms 程度リングバッファに溜め、通知が来たら遡って送る**。

既定動作の抑止が可能である根拠: `Team Voice Chat` などの既存プラグインが、通常の近接ブロードキャストを止めてチームだけに配信している。

## デプロイ

### systemd

```ini
[Unit]
Description=Rust proximity voice relay
After=network-online.target

[Service]
User=voicerelay
ExecStart=/opt/voicerelay/voicerelay
AmbientCapabilities=CAP_NET_BIND_SERVICE
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

`AmbientCapabilities` により非 root のまま 443 を bind できる。

### 必要なポート

| ポート | 用途 |
|---|---|
| 443/tcp | PWA 配信 + シグナリング + ACME (TLS-ALPN-01) |
| UDP × 1 | 音声。**str0m は全トラフィックを 1 つの UDP ソケットに多重化する** |

WebRTC で通常必要な UDP レンジの開放が要らない。

### 前提

- **DNS 名が必須**（マイク許可に HTTPS が要る）。ゲームサーバーの IP に A レコード 1 本
- 証明書は `rustls-acme` が自動取得・自動更新。80 番は不要

## 実装順

1〜4 は **Rust ゲーム抜きで完成させられる**。プラグインは最後に置き、そこまでに不確実性を潰しておく。

| # | 作るもの | 単体で確認できること |
|---|---|---|
| 1 | リレー（str0m の SFU example が土台）+ 静的配信 | ブラウザ 2 枚で通話が成立する |
| 2 | PWA に Web Audio の減衰・定位 + ダミー座標スライダー | 距離で音量が変わる |
| 3 | 認証（Steam OpenID・名簿 push・HMAC・TTL・即時失効） | 他人が入れない / 抜けたら切れる |
| 4 | systemd + ACME | 再起動しても上がる |
| 5 | Oxide プラグイン（可聴集合・V キー検出・CUI HUD） | 実サーバーで繋がる |

### 既知の罠

- **Chrome で WebRTC のトラックを Web Audio に流すと音が出ないことがある。** 同じストリームを muted な `<audio>` 要素にもアタッチするのが定番の回避策。距離減衰が全部ここに乗るので、最初に潰しておく

## 検討して却下した設計

同じ道を辿り直さないための記録。

### ゲーム内 VC をプラグインで改善する

**却下** — 中継はゲームのメインループ上で起きるため、拠点の server fps 低下と負荷の座標が一致する。二次の増加を消せない。

ただし**声の届く範囲を縮めれば扇形は小さくなる**。`VoiceLimiter` / `Voice Levels` が既に存在し、開発ゼロで試せる。**このプロジェクトに着手する前に、まずそれで足りるか確認すべき。**

なお「Rust の voice proximity はハードコードで変更不可」という古い情報が uMod のコミュニティ回答に残っているが、**誤り**。`Team Voice Chat`（距離を無視してチームに配信）、`VoiceLimiter`（範囲変更）、`CRadio` が実在する。受け手の集合はプラグインから完全に制御できる。

### Discord のボイスチャンネル + bot

**却下** — proximity は本質的に **N×M の行列**だが、bot が操作できるのは**長さ N のベクトル**（mute か / どのチャンネルか）しかない。

決定的な反例: proximity では「A は B が聞こえ、B は C が聞こえ、A は C が聞こえない」が日常的に起きる。この非推移的な関係を、チャンネルという排他的なグループ分けで表現する方法は存在しない。

### bot をプレイヤー人数ぶん立てる

**却下** — bot は 1 ギルドにつき 1 ボイスチャンネルにしか入れないため、50 人なら bot アプリ 50 個。さらに **音声受信は Discord の公式サポート外**（discord.js 自身が「破損する可能性がある」と明記）。そしてミキシングを自前で書くことになるので、**自前リレーと同じ実装量を書いたうえで Discord の制約を被る**下位互換。

### Discord Social SDK（ネイティブ）

**却下** — 通話は **25 人以下推奨**。拠点ごとに lobby を分けると移動のたびに join/leave が発生し、**lobby 作成/参加 100 回 / 2 時間**の制限に当たる。

参考値: lobby の人数上限は 1,000、メンバーは切断しても抜けない（明示的な leave のみ）、通話の開始はレート制限対象外。lobby を 1 個固定にして距離処理を全部クライアント側でやれば、身内規模ならレート制限には当たらない。

### Discord Social SDK（PWA / Activity）

**却下** — Embedded App SDK のコマンド一覧に `setUserVoiceSettings` が存在しない。volume と pan は `VOICE_STATE_UPDATE` イベントで**読めるが書けない**。

### Discord ローカル RPC + ネイティブ常駐アプリ

**保留（有力な代替案）** — `SET_USER_VOICE_SETTINGS` は聞き手のローカル設定なので、**N×M の行列が各クライアントのローカルで解決する**。距離 → volume(0-200)、方向 → pan(left/right 各 0.0-1.0) に変換するだけで、Opus もリレーも WebRTC も不要。実装は本プロジェクトより桁で小さい。Among Us 向けの [CrewComms](https://github.com/Frazew/CrewComms) が同じ方式で動いている。

**制約:**
- `rpc.voice.write` は Discord の承認が必要。ただし **未承認でもテスター枠 50 人までは動く**
- 承認済みアプリは世界で 4 つ（Overlayed / Reactive Images / Discord Streamkit / Elgato Streamdeck）。**新規に開く扉ではない**
- **ブラウザはローカル RPC WebSocket に接続できない**（origin 検証）。ネイティブアプリ確定 = PWA と両立しない
- 全員が同じ Discord VC に入る必要がある。アプリ未起動の人には全員フル音量で聞こえる
- voice settings を変更できるアプリは同時に 1 つだけ（Streamdeck 等と競合）

**判断: 50 人以下ならこちらのほうが小さい。** ただし上限に当たった時の移行先が本プロジェクトであり、**Oxide プラグイン（座標の絞り込み）は両案で共通**なので手戻りは小さい。

### WebSocket + WebCodecs（WebRTC の代わり）

**却下** — 実装は小さいが、**ジッタバッファ・パケットロス補償・クロックドリフト補償を自前で書くことになる**。realtime audio で最も難しい部分であり、WebRTC はそれを丸ごと提供する。

### プラグインからブラウザを開く

**却下** — 複数の Oxide スレッドで「URL の扱いはクライアント側のみ、サーバーからは制御できない」で一致。`Application.OpenURL` はサーバー上で走るため無意味。

代わりに **PWA を常時開いておき、ゲームにログインした瞬間に自動で音声を開始する**。毎回リンクを踏むより体験が良い。初回の導線には `server.url` を PWA に向けておく手がある。

## 前例・参考

- **[Simple Voice Chat](https://modrinth.com/plugin/simple-voice-chat)**（Minecraft, 117.6M DL）— サーバー MOD + クライアント MOD + 専用 UDP リレー（既定 24454, Opus）。サーバーが「誰と誰が近いか」を計算し、各プレイヤーに聞こえるべき声だけを送る。**本プロジェクトとほぼ同じ構成が大規模で実証済み**
- **[voicechat-proximity](https://github.com/sogladev/voicechat-proximity)**（AzerothCore）— C++ プラグイン → WebSocket → Go バックエンド → WebRTC → Web Audio API でピアごとに音量計算。ブラウザ側の前例
- **[CrewComms](https://github.com/Frazew/CrewComms)**（Among Us）— Discord ローカル RPC の音量設定を使った proximity
- **Rust+ 公式コンパニオンアプリ** — 外部アプリがゲームサーバーの状態を受け取る構成は、このゲームで公認済み

## なぜ Rust ゲームに前例が少ないか

Minecraft には音声機能が**ゼロ**だったため Simple Voice Chat は空白を埋めた。Rust には既に近接音声があり、範囲調整・チーム音声・ラジオはプラグインで満たされている。残っているのは連続的な減衰カーブ・遮蔽・残響という**質の話**。

加えて、Rust にはクライアント MOD 文化が無く（EAC）、月次 wipe で人口が流動的、プレイヤーは敵対関係にあり、座標を配る設計は忌避されやすい。Facepunch 自身も Voice Props DLC（拡声器・マイク・カセット・電話・留守番電話）で音声機能を拡張し続けている。

**本プロジェクトの価値は「聞こえる / 聞こえない」を「どう聞こえるか」に変えることに絞られる。** 連続的な減衰、壁の遮蔽、残響。それが欲しいかどうかが着手の判断基準。
