## 0. 不変条件

```
このシステムは、ゲーム内 VC が聞かせる以上を聞かせない。
```

個々の失効ルールはここから導く。迷ったら**ネイティブの挙動を実測して合わせる**。

| 事象 | 扱い | 根拠 |
|---|---|---|
| 切断 / Alt-F4 / クラッシュ | **必須で失効** | ログアウト後はゲーム内に存在しない。聞こえたらゲームに無い能力を与えたことになる |

### ★ 失効 = RTP 転送の停止であって、WebRTC の切断ではない

必要な安全性は「聞こえてはいけない音声が届かないこと」であり、それは**リレーが転送しない**ことで満たされる。
サーバー側の判断なので改造クライアントには覆せず、切断と同じ強度でコストがゼロ。

| 事象 | 動作 |
|---|---|
| 死亡 / リスポーン | 転送停止 / 再開。**再ネゴシエーションしない** |
| 可聴範囲の出入り | スロットの割り当て / 解放。**再ネゴシエーションしない** |
| 切断（ログアウト） | 即座に転送停止 → 猶予 60s 後にトランスポート回収 |
| roster TTL 切れ | 全員へ転送停止 |
| **二重接続 / BAN / shutdown** | ここだけ `bye` を送って本当に切る |

（「購読したまま gain 0」を禁じたのは**クライアント側の gain** の話。サーバー側の転送停止とは別物で、
後者が本来の境界線。）

| スリープ | 自動的に失効 | 未接続なので名簿に載らない。特別扱い不要 |
| **死亡** | **設定 `revoke_on_death`（既定 true）** | ネイティブが死亡中に聞かせるかは**未実測**。実測して合わせる。#1-4 の宿題 |
| 管理者の BAN / mute | 失効 | 運用要件 |
| 同一 SteamID の二重接続 | 後勝ちで前を切る | セッション乗っ取りの防止 |

死亡については、`hears` を位置から計算する以上、死亡中のプレイヤーの位置をどう扱うかで
自然に決まる部分もある（死体位置で計算するか、空集合を返すか）。
**ネイティブの挙動を確認するまでは既定 true（切る）** で進める。

## 定数

| 名前 | 値 | 意味 |
|---|---|---|
| `AUDIBLE_M` | 60 | 声が届く距離。これを超えると gain 0 |
| `SUBSCRIBE_M` | 75 | 購読を張る距離。60〜75m は購読済みだが gain 0（ヒステリシス） |
| `GRAPH_HZ` | 2 | 可聴グラフの更新レート。**変化が無ければ送らない** |
| `YAW_HZ` | 20 | 聞き手の向きの更新レート。u16 が 1 個だけ |
| `SLOTS` | 16 | 音声受信スロット数。可聴人数がこれを超えたら近い順 |
| `ROSTER_INTERVAL_S` | 2 | 名簿の push 間隔 |
| `ROSTER_TTL_S` | 10 | この時間 roster が来なければ **全セッションを切る**（fail closed） |
| `DIST_QUANT_M` | 1 | 距離の量子化幅 |
| `BEARING_QUANT_DEG` | 5 | 方位の量子化幅 |
| `HMAC_SKEW_S` | 30 | プラグイン→リレーの署名で許容する時刻ずれ |
| `revoke_on_death` | true | 死亡時に失効させるか。**実測して決める**（§0） |

## 1. プラグイン → リレー（server-to-server, HTTPS + HMAC）

全リクエストに以下のヘッダを付ける。

```
X-PV-Timestamp: <unix秒>
X-PV-Signature: <hex(hmac_sha256(secret, timestamp + "." + body))>
```

検証は 3 点。**どれか 1 つでも欠けたら 401**。

1. 署名一致（定数時間比較）
2. `|now - timestamp| <= HMAC_SKEW_S`
3. `seq` が **`(server_id, endpoint)` ごと**に単調増加（巻き戻りは破棄）

**★ `seq` の採番は endpoint ごとに独立（親が確定、2026-08-26）**

`roster` / `graph` / `yaw` / `talk` は**それぞれ別の counter**を持つ。`server_id` 単位で
1 本にすると、レートの違う stream が互いを巻き戻し扱いして 401 が出続ける
（`roster` は 0.5 Hz、`yaw` は 20 Hz）。検証側のキーは `"roster:main"` `"graph:main"` の形。

**`yaw` と `talk` にも `seq` がある。** 初版は付けていなかったが、`talk` の
リプレイは**本人が V を押していないのにマイクが送信状態になる**（ホットマイク）ため、
30 秒窓のリプレイを許容できない。#1-3 の指摘で追加した。

### `POST /internal/roster`

```json
{
  "server_id": "main",
  "seq": 8412,
  "ts": 1756180000,
  "eligible": ["76561198000000001", "76561198000000042"]
}
```

- **差分ではなく毎回フル**。受信側は置き換える
- `eligible` に居ない SteamID のセッションは即座に切る
- 最終受信から `ROSTER_TTL_S` を過ぎたら、その `server_id` の全セッションを切る

### `POST /internal/graph`

`GRAPH_HZ` で送る。**絶対座標を含めてはならない。**

```json
{
  "server_id": "main",
  "seq": 90211,
  "ts": 1756180000,
  "listeners": [
    {
      "id": "76561198000000001",
      "hears": [
        { "id": "76561198000000042", "d": 23, "b": 145, "sub": true }
      ]
    }
  ]
}
```

| フィールド | 型 | 意味 |
|---|---|---|
| `id` | string | 相手の SteamID64 |
| `d` | u16 | 距離 (m)。`DIST_QUANT_M` 刻み |
| `b` | u16 | **世界座標系での方位** (度、0-355)。`BEARING_QUANT_DEG` 刻み。相対方位は PWA が `yaw` を引いて出す |
| `sub` | bool | 購読すべきか。`d <= SUBSCRIBE_M` |

`sub: false` になった相手は、リレーが RTP 転送を止める。**購読していないことが唯一の保証**であり、
「購読したまま gain 0」は禁止（改造クライアントが gain を戻せる）。

### `POST /internal/yaw`

`YAW_HZ` = 20 で送る。**graph とは別便**。1 tick = 1 リクエストに全聞き手ぶんを詰める。

```json
{ "server_id": "main", "seq": 55120, "ts": 1756180000, "yaws": [["76561198000000001", 145]] }
```

### `POST /internal/talk`

PTT の状態変化。押下・離しの都度、即時に送る。

```json
{ "server_id": "main", "seq": 311, "ts": 1756180000, "id": "76561198000000001", "talking": true }
```

## 2. ブラウザ ↔ リレー

### 認証（Steam OpenID）

| 経路 | 動作 |
|---|---|
| `GET /auth/steam` | Valve へリダイレクト |
| `GET /auth/steam/return` | 署名検証 → SteamID64 確定 → セッショントークン発行 → `/` へ |

**画面に秘密を出さない。** ペアリングコードもトークン付きリンクも使わない（配信対策）。
トークンは HttpOnly Cookie で渡す。

### `GET /ws`

WebSocket。Cookie のトークンで認証する。

**Client → Server**

```json
{ "t": "hello", "v": 1 }
{ "t": "sdp_offer", "sdp": "..." }
{ "t": "ice", "candidate": { } }
```

**Server → Client**

```json
{ "t": "ready",      "steam_id": "7656...", "server_id": "main" }
{ "t": "sdp_answer", "sdp": "..." }
{ "t": "ice",        "candidate": { } }
{ "t": "peer",       "id": "7656...", "mid": "1" }
{ "t": "graph",      "hears": [ { "id": "7656...", "d": 23, "b": 145, "sub": true } ] }
{ "t": "talk",       "on": true }
{ "t": "bye",        "reason": "roster_expired" }
```

- **`peer` は必須。** PWA は複数の音声トラックを受け取るので、RTP の `mid` と SteamID の
  対応が無いと誰の声か分からない。`"id": null` はそのスロットの解放を意味する
- `graph` は `GRAPH_HZ` で流れる。**そのブラウザが聞ける相手だけ**が入る
- `talk` は自分の PTT 状態。`on: true` を受けたらマイク送信を開始する
- `bye` の `reason`: `roster_expired` / `not_eligible` / `duplicate_session` / `server_shutdown`

### スロットプール（再ネゴシエーションを起こさないための要）

人が可聴範囲を出入りするたびにトラックを付け外しすると、**そのたびに SDP 再ネゴシエーションが走る**。
歩き回るだけで頻発するので、これを構造的に避ける。

```
接続時に音声受信スロットを SLOTS 本まとめて張る（ネゴシエーションはこの 1 回だけ）
   ↓
範囲に入る → 空きスロットに割り当て → { "t":"peer", "mid":"3", "id":"7656..." }
範囲を出る → スロットを解放         → { "t":"peer", "mid":"3", "id":null }
```

#### ★ m-line を並べるのは offer 側 = PWA（親が確定、2026-08-26）

**SDP の answer は m-line を増やせない。** したがって「サーバーが 16 本張る」は成立しない
（初版の記述は誤りだった。#1-2 の指摘で訂正）。offer を出す PWA が最初から並べる。

| 順序 | m-line | 向き（PWA 視点） |
|---|---|---|
| 先頭 | マイク × 1 | `sendonly` |
| 以降 | 受信スロット × `SLOTS` (=16) | `recvonly` |

**マイクを先頭に固定する理由**: `SLOTS` を将来変えても、スロットが末尾に追加/削除されるだけで
マイクの位置が動かない。逆順にすると `SLOTS` の変更でマイクの mid がずれる。

- **mid の値を決め打ちしない。** PWA は `ontrack` の `transceiver.mid` でスロットを引く。
  サーバーは `ServerMsg::Peer { mid, id }` で対応を伝える。両者とも文字列としてしか扱わない
- **再ネゴシエーションは一切行わない。** サーバーから offer は送らない
- サーバー（str0m）は answer で `recvonly` の各 m-line を `sendonly` として受け、
  そこへ転送先の RTP を載せる

**以後、再ネゴシエーションは一切起きない。** 可聴人数が `SLOTS` を超えたら距離の近い順に選ぶ。

**★ タスク跨ぎの契約 (親が確定、2026-08-26)**

| | |
|---|---|
| `SfuCommand::SetSubscriptions` の `speakers` | **距離の近い順に並んでいること**。並べる責任は呼び出し側 (graph を持つ `roster.rs`)。SFU 側は先頭 `SLOTS` 件に切り詰めるだけ |
| `SfuCommand::MuteAll` | **スロット割り当てを保持したまま転送だけ止める。** 解放して `Peer{id:null}` を撒くと、死亡/リスポーンのたびに PWA 側でスロットが動いて音が飛ぶ。`SetSubscriptions` を呼ぶと mute が解ける (= 転送停止 / 再開) |
| 既に割り当て済みの相手の `mid` | `SetSubscriptions` を連続で呼んでも**変わらないこと**。変わると PWA 側の音が途切れる |

### yaw は graph と分けて送る

変化の速さが違うものを同じレートで送らない。

| 量 | レート | 大きさ |
|---|---|---|
| `graph`（可聴集合 + 距離 + 世界方位） | `GRAPH_HZ` = 2、**変化時のみ** | 人数 × 数十バイト |
| `yaw`（聞き手の向き） | `YAW_HZ` = 20 | **u16 が 1 個** |

振り向きは一瞬で 180° 変わるので追従性が要るが、それは 2 バイトのスカラー 1 個で足りる。
可聴集合と距離は歩行速度でしか変わらないので 2 Hz で十分。静止中は graph が飛ばない。

```json
{ "t": "yaw", "deg": 145 }
```

## 3. PWA 側の音の作り方

リレーもプラグインも音量を計算しない。**PWA が `d` と `b` から自分で作る。**

```
gain(d) = 0                          (d > AUDIBLE_M)
        = 1.0                        (d <= 5)
        = (1 - (d - 5) / 55) ^ 1.5   (5 < d <= AUDIBLE_M)

bearing = (b_world - yaw + 360) % 360     // b_world は graph、yaw は 20Hz で届く
pan     = sin(bearing * PI / 180)         // StereoPannerNode の -1.0 .. 1.0
```

`sub: true` かつ `d > AUDIBLE_M` の相手は、**接続は張ったまま gain 0**。
60m を切ったところで滑らかにフェードインする（ヒステリシス）。

## 4. PTT の流れ

```
V 押下 → Rust が音声をサーバーへ送る
      → プラグインの OnPlayerVoice が発火
      → プラグインが既定のブロードキャストを抑止（ネイティブ音声は流さない）
      → POST /internal/talk { talking: true }
      → リレーが該当ブラウザへ { "t": "talk", "on": true }
      → PWA がマイク送信を開始
```

サーバー往復ぶん遅れるため、**PWA は常時 300ms のリングバッファにマイクを溜め、
`talk on` を受けたら遡って送る**。最初の音節を落とさないため。
